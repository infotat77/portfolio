バックグラウンド自動化を長期運用して踏んだ5つの落とし穴

Mac の launchd と cron で複数の自動化ボットを常時稼働させています。作った直後は動いても、 数週間・数か月と放置すると静かに壊れる。「PCのファンがうるさい」という素朴な違和感から棚卸しを始めたら、 止まっていた処理・空回りしていた処理が次々に出てきました。運用して初めてわかった落とし穴と、その直し方をまとめます。

発端：ファンがずっとうるさい

きっかけは「最近ずっとファンが唸っている」という違和感でした。原因の切り分けは実測から。 ps -Ao pid,pcpu,comm -r と uptime を叩くと、ロードアベレージが 32 という 異常値。4コア8スレッドのマシンで 32 は完全な過負荷です。犯人は動画エンコードの ffmpeg が CPU を 300% 以上使いながら数時間回り続けていたことでした。

ここから芋づる式に、止まっていたジョブ・空回りしていたジョブが見つかります。以下、見つかった順に。

落とし穴 1：CPUエンコードで非力なマシンを焼き続ける

動画の書き出しに libx264（CPUエンコード）を -crf 18（ほぼ無劣化）で使っていました。 高画質ですが、省電力なモバイル向けCPUには荷が重すぎます。この機種には Quick Sync（h264_videotoolbox）という ハードウェアエンコーダが載っていたので、専用回路にオフロードしました。

差し替える前に、短尺クリップで画質・サイズ・所要時間を実測して比較しました。

設定所要時間サイズSSIM
libx264 crf18（旧）56秒45.0 MB0.9952
libx264 crf2349秒27.5 MB0.9913
videotoolbox 12M（新）6秒43.2 MB0.9924

処理時間はおよそ 9倍速。SSIM（元動画との類似度）の差は 0.3% で、対象が静止画に近い映像なら 目視では判別できません。しかも配信先で再エンコードされるため、この差は視聴者に届きません。 CPUを使わなくなったのでファンは静かになり、ロードアベレージは 32 → 2.2 に落ちました。

Apple Silicon だと思い込んでいたマシンが、実際は Intel でした。sysctl -n machdep.cpu.brand_string で確認する。ハードウェアエンコーダの有無や名前は世代で変わるので、思い込みではなく ffmpeg -encoders | grep videotoolbox で実在を確かめてから使う。

落とし穴 2：cron の中で venv が無効になっていた

あるパイプラインが 39日間、6時間おきに起動しては即エラーで死んでいました。 ログには同じ ModuleNotFoundError が 156回。原因は cron の一行にありました。 

# ❌ venv を有効化した直後に、絶対パスで別の python を呼んでいる
source venv/bin/activate && /usr/local/bin/python3 script.py

# ✅ venv の python を直接叩けば activate すら要らない
./venv/bin/python3 script.py

activate は環境変数を書き換えるだけで、フルパス指定の python3 はそれを無視します。 結果、venv の外の python が動き、依存パッケージが見つからず落ちる。手元で source activate してから python と打つ癖があると、この罠は見抜きにくいです。 cron やスクリプトでは 常に venv 内の実行ファイルを絶対パスで指すのが確実です。

落とし穴 3：OAuth トークンがテストモードで7日失効する

Google 系 API を使う処理が invalid_grant: Bad Request で全滅していました。 リフレッシュトークンが失効していたのです。原因は Google Cloud Console の OAuth 同意画面が 「テスト中」のままだったこと。この状態だとリフレッシュトークンは 7日で失効します。

「アプリを公開（本番環境）」に切り替えれば失効しなくなります。個人利用なら審査は不要で、 ステータス変更だけで済みます。ただし切り替え前に発行したトークンは7日ルールのままなので、 公開後に取り直す必要があります。

じつはこの教訓、過去に一度別のプロジェクトで学んで記事にも書いていました。にもかかわらず別プロジェクトで 再発。「7日で切れる」は忘れた頃にやってくるので、再認証を促すフォールバックをコード側に用意しておくと復旧が早いです。 
# refresh に失敗したらブラウザ認証へ落ちるようにしておく
try:
    creds.refresh(Request())
except RefreshError:
    creds = None  # 下でブラウザ認証フローを実行

落とし穴 4：whisper.cpp に動画を直接渡していた

音声を文字起こしする工程が、失敗はしないのに結果が常に空という厄介な壊れ方をしていました。 whisper-cli に mp4 を直接渡していたのが原因です。whisper.cpp は動画から音声を抽出できず、 無音として処理してしまいます（ログの mel time = 0.00 ms がサイン）。 

# 事前に 16kHz / モノラルの WAV へ変換してから渡す
ffmpeg -i input.mp4 -ar 16000 -ac 1 -c:a pcm_s16le audio.wav
whisper-cli -m model.bin -f audio.wav -oj

エラーで止まらず「動いているように見えて中身が空」というのが一番見つけにくい壊れ方でした。

対策：「動いてるつもり」を潰す死活監視

今回の学びは、自動化は作った瞬間ではなく放置した後に壊れるということ。 そこで各ジョブのログを毎朝点検し、異常があれば通知するスクリプトを仕込みました。見るのは2点だけです。

  • ログの鮮度 — 想定周期より古ければ「そもそも動いていない」
  • 直近の実行分にエラー痕跡があるか — Traceback などのマーカーを探す

毎日同じ警告が飛んで麻痺しないよう、状態をファイルに保存し 「壊れた瞬間」と「復旧した瞬間」だけ通知します。ログを実行単位で切り分けたいので、 各ジョブの先頭に実行時刻を出力しておくと点検が楽になります。

まとめ

  • 異常は感覚ではなく uptime / ps / ログの実測で切り分ける
  • 重い処理はハードウェアにオフロードできないか疑う。差し替え前に必ず数値で比較する
  • cron・スクリプトでは実行ファイルを絶対パスで指す。環境が思い込み通りとは限らない
  • OAuth のテストモード7日失効のような「時限爆弾」は、フォールバックと監視で受け止める
  • エラーで止まらない壊れ方こそ怖い。死活監視で「動いてるつもり」を潰す
